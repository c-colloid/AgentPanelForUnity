# 2026-11-28 -- 長いセッションでリロード後の表示が遅い(カード詳細と画像の遅延構築)

## 発端

ユーザーからの指摘: 「リロードが起きたときに、最初から全部の表示を頭から読み込み直して
いるように見える。セッションが長くなると再読み込みの時間が長くなる。必要な分だけ読み込み、
古いログは非同期で読む形にした方がよいのではないか。スクロール表示は仮想化されているのか」。

## 先に結論

- 表示は仮想化済み(`2026-09-30-transcript-virtualization.md`)。ただし仮想化の単位は
  **メッセージ**で、アシスタントの発言は **1 ターンが 1 メッセージ**になる。ツールを 200 回
  呼ぶターンは数百ブロックの 1 行で、その行は丸ごと生きている。
- 遅さの正体は読み込みではなく **行の構築**だった。閉じているカードの中身(入力・結果・
  差分)と、畳まれたグループの中のカードを全部作っており、さらにツール結果の画像を
  行の構築中に同期でデコードしていた。
- セッションキャッシュの保存・読み込みと、CLI 中継の行の流し直しは、測ると小さかった。
  どちらも今回は変えない。

## 計測

`C:\Unity\UnityProjects\PanelPerf`(`ci/HostProject` の ProjectSettings + Core だけの manifest)で
`-batchmode -executeMethod`。実際のパネルセッションの CLI トランスクリプトを
`TranscriptLoader` で `ChatSession` に戻し(ライブ経路と同じ形になる)、リロードが触る処理を
個別に測った。対象は 2026-11-28 の実セッション(jsonl 76.3 MB、58 メッセージ、3,060 ブロック、
ツール 1,999 回、1 メッセージ最大 309 ブロック)。行の構築はパネルに付けない状態での
要素生成だけの時間で、スタイル解決とレイアウトは含まない(要素数に比例して上乗せされる)。

| 項目 | 変更前 | 変更後 |
|---|---|---|
| セッションキャッシュ(2.84 MB)保存 | 40〜80 ms | 同じ |
| セッションキャッシュ読み込み | 40〜165 ms | 同じ |
| 最大ターンの生の行(357 行、7.4 M 文字)を `JsonParser.Parse` | 30〜40 ms | 同じ |
| リロード後に作る 24 行の構築 | 1,303〜2,809 ms | 109〜127 ms |
| 全 58 行の構築 | 2,582 ms | 109 ms |
| 最大の行(309 ブロック)1 回の構築 | 118.6 ms / 13,284 要素 | 8.3 ms / 1,332 要素 |
| 同じ行をブロック追加のたびに作り直した合計(309 回) | 22,402 ms | 2,592 ms |

中間の計測(カード詳細とグループの遅延だけを入れた段階)では 24 行が 633〜799 ms 残った。
ツールカードのコンストラクタを区間ごとに測ると、1,999 枚の合計 約 1,170 ms のうち
933 ms が結果画像の帯(`BuildImageStrip` → `ImageThumbnailCache.Get`)だった。

### 外れた見立て

最初はコードを読んで「セッションキャッシュを毎回全件保存・全件読み込みしている」ことを
原因と考えた。全件処理なのは事実だが、実データでは 3 MB 未満・100 ms 前後で、体感の
秒単位の遅さは説明できない。CLI 中継の再接続が開いているターンの行を流し直す点も同様に
小さい(パースは数十 ms、20 行/フレームで 18 フレーム)。コードの形からの推測ではなく
計測で決めるべき例として残す。

## 原因

1. **`ToolActivityCard` が詳細を先に作る。** コンストラクタが `BuildDetails` を呼び、
   `display: none` で持っていた。入力 JSON はチャンクごとの Label、Write/Edit の差分は
   1 行 1 Label(プレビュー 40 行)なので、閉じたカード 1 枚が数十〜数百要素になる。
2. **グループ行が中のカードを先に作る。** 完了したツールが 3 個以上続くと 1 行に畳むが、
   畳んだ中の `ToolActivityCard` を全部作っていた(1 の詳細つき)。
3. **`SubagentCard` が入れ子のトランスクリプトを先に作る。** 最大 120 ブロックと要約の
   Markdown。
4. **画像を行の構築中にデコードする。** `MessageBlockFactory.CreateImageBlock` が
   `ImageThumbnailCache.Get` を同期で呼ぶ(ファイル読み込み + フルサイズのデコード)。
   キャッシュは 32 枚で、ドメインリロードで空になる。スクリーンショットを多く返すターンでは、
   リロードのたびに生きている行の画像を全部デコードし、32 枚を超える分は行の作り直しの
   たびにまたデコードしていた。
5. 1〜4 は、行が構造的に変わるたびに丸ごと作り直される(`MessageListController.Refresh`)
   ことで増幅される。1 行 = 1 ターンなので、ターンが長いほど 1 回の作り直しが重くなる。

## 対策

見えていないものは作らない。見えるものでも、重い処理は行の構築から外す。

- `ToolActivityCard`: 詳細は最初に開いたときに作る(`SetExpanded`)。開いた状態を覚えて
  いるカード(`ExpandedByToolUseId`)は、従来どおり作り直し時に開いた状態で作られる。
  閉じても詳細は捨てない。
- グループ行: 中のカードは最初に開いたときに作る。入れ物(`uap-toolgroup-children`)は
  今までどおり最初からある。
- `SubagentCard`: `PopulateDetails` は最初に開いたとき。履歴から戻した入れ子ブロックの
  遅延読み込み(`TryLazyLoadNestedBlocks`)の後に走る。
- 画像: `CreateImageBlock` は枠(`Image`、大きさは USS で固定なのでレイアウトは動かない)
  だけ作る。キャッシュにあれば即座に入れ(`ImageThumbnailCache.Peek`、ファイルは読まない)、
  なければ `DeferredThumbnails.Request` に預ける。`DeferredThumbnails` は
  `EditorApplication.update` で 1 ティックあたり 8 ms を目安に(最低 1 枚)デコードする。
  要素がパネルに付いていない依頼は捨てる(作り直しや仮想化で捨てられた行の分は
  デコードしない)。後から付いた要素は `AttachToPanelEvent` で自分から頼み直す。
  デコードできないファイルは、今までどおり「見つからない」の表示になる。
  キャプションの寸法(幅×高さ)は画像が入った時点で付く。

### 検討して見送ったもの

- **セッションキャッシュを直近分と古い分に分けて非同期で読む**(元の提案)。計測では
  100 ms 前後で、分割・追記型にする複雑さ(原子的な書き込み、読めなかったときの上書き
  防止 `2026-09-12-session-cache-transient-read-failure.md` との両立)に見合わない。
  キャッシュが数十 MB になるセッションが実際に出たら再検討する。
- **行の中をブロック単位で差分更新する / 仮想化の単位をブロックにする。** 今回の対策で
  最大の行の作り直しが 8 ms になったので、いまは不要。ターンがさらに長くなり、
  1 回の作り直しが 60 ms の更新間隔に近づいたら次の手になる。
- **サムネイルを縮小して持つ。** フルサイズのテクスチャを 32 枚持つメモリの問題は残る
  (32 枚を超えると古い画像のテクスチャが破棄される既存の挙動も同じ)。別件として扱う。

## 回帰ガード

`Tests/Editor/LazyCardContentTests.cs`:

- 閉じたツールカードは詳細を作らない。開くと作り、閉じても同じ要素を持ち続ける。
  開いた状態を覚えているカードは開いて作られる。
- 閉じたグループ行は中のカードを作らない。開いた状態を覚えていれば全部作る。
- 閉じたサブエージェントカードの詳細は空で、開くと入る。
- 画像ブロックは構築時にデコードしない。ポンプが 1 回回ると入り、同じファイルの次の
  ブロックは即座に入る。捨てられた要素の依頼はデコードされない。予算 0 でも 1 ティックに
  1 枚は進み、1 枚しか進まない。無いファイルはプレースホルダーになる。

既存の `MessageBlockFactoryExpandStateTests` / `ToolActivityCardExpandStateTests` /
`SubagentCardExpandStateTests` / `AgentHubToolResultImageTests` はそのまま通る
(入れ物の要素と開閉状態の扱いは変えていない)。

## 残り

- 実機(GUI)でのスクロール・リロードの体感は未確認。計測は要素生成の時間だけで、
  スタイル解決とレイアウトは要素数の減少(最大の行で約 1/10)から見込んでいる。
- Unity 自体のドメインリロード時間はパネルの外で、今回の対象外。
