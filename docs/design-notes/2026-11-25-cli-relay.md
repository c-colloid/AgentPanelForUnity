# 2026-11-25 -- CLI 中継(ドメインリロードをまたいで CLI を動かし続ける)

発端: 「ドメインリロードのたびに CLI を一時停止して、再開時にもう一度命令を出している。
リロード中も裏で CLI を動かしておくのはダメなのか」というユーザーの問い。

参照: `docs/design-notes/2026-09-06-domain-reload-resilience-and-hot-reload.md`(今の
「止めて `--resume` で戻す」方式)、`docs/research/08-mcp-transport.md`(MCP の接続と
タイムアウトの実測)、`docs/design-notes/2026-11-23-request-checkpoints.md`(依頼ごとの
チェックポイント)、`Editor/Integration/ReloadLifecycle.cs`。

---

## 0. 結論(先に)

- CLI を Unity の子プロセスにしている限り、リロードでは止めるしかない。標準入出力の
  パイプを持っている側(Unity の AppDomain)が作り直されるからである。
- そこで **CLI の親を小さな中継プロセスに移す**。中継は CLI の標準入出力を持ち続け、
  Unity とはループバックの TCP でつながる。リロードのとき Unity は接続を閉じるだけで、
  CLI は止まらない。新しいドメインは同じ中継につなぎ直し、切れていた間の出力を受け取る。
- 効果: リロードをまたいでもターンが切れない。割り込み、`--resume` での再起動、
  「続けて」の再送が要らなくなり、その分のトークンと待ち時間が消える。
- **既定は OFF** の設定(設定 > Unity 連携 > Unity操作(UapOps)「スクリプトのリロード中もエージェントを動かし続ける(実験的)」)として
  入れる。対象は Claude Code のみ。うまくいかない場合はすべて今までの
  「止めて再開」に落ちる(§7)。

---

## 1. 今の方式で失っているもの

リロード前(`beforeAssemblyReload`)に割り込みを送って CLI を終了させ、リロード後に
`--resume` で起動し直す。ターンの途中だった場合は「中断された」として扱い、設定に
よっては「続けて」を自動で送る。

- ターンが切れる。実行中だったツールは中断され、モデルは続きを組み立て直す。
- 再起動のたびにシステムプロンプトと会話履歴を読み直す(キャッシュが効いても待ちが出る)。
- 承認待ちのカードはリロードで消え、あとから「承認待ちが失われた」と知らせるしかない。
- スクリプトを書かせる作業ほどリロードが多く、この損失が積み重なる。

## 2. 構成

```
Unity Editor (AppDomain は何度も作り直される)
   │  制御リンク: 127.0.0.1 の TCP、1 行 1 フレーム
   ▼
cli-relay (dotnet、Unity とは別プロセス。リロードを越えて生き続ける)
   │  標準入出力のパイプ                 ▲ MCP (HTTP)
   ▼                                     │
claude CLI ─────────────────────────────┘
```

- 中継プログラムは `Editor/Tools~/UapCliRelay/`(`CliRelayCore.cs` と
  `CliRelayMain.cs`)。Unity に同梱されている .NET ランタイムとコンパイラで、
  パッケージの版ごとに一度だけビルドする。既存の stdio 中継と同じ
  `UapStdioRelayBuilder` を一般化して使う(`RelayProgram`)。出力先は
  `Library/UnityAgentPanel/CliRelay/<ハッシュ>/cli-relay.dll`。
- Unity 側の窓口は `Editor/Core/Process/RelayCliTransport.cs`。`ICliTransport` の実装で、
  `AgentClient` から見れば今までの `ClaudeCliProcess` と同じに見える。

### 2.1 制御リンク

1 行が 1 フレーム。先頭 1 文字が種類を表す。

| 向き | フレーム | 中身 |
|---|---|---|
| 中継 → Unity | `O <行>` | CLI の標準出力 1 行 |
| 中継 → Unity | `E <行>` | CLI の標準エラー 1 行 |
| 中継 → Unity | `C <json>` | `welcome` / `spawned` / `spawnFailed` / `live` / `exited` / `rejected` / `bye` |
| Unity → 中継 | `I <番号> <行>` | CLI の標準入力へ書く 1 行。番号は通し番号 |
| Unity → 中継 | `C <json>` | `hello` / `spawn` / `ack` / `backend` / `detach` / `shutdown` |

- 最初のフレームは必ず `hello`(トークン付き)。トークンは環境変数で中継に渡し、
  コマンドラインには載せない。中継は CLI に渡す環境からこの変数を取り除く。
- `hello` と `welcome` はプロトコル番号を運ぶ。合わなければつながずに止める。
  `shutdown` の形だけは将来も変えない(古い中継を新しいパッケージが止められるように)。
- CLI の起動引数はファイル経由で渡す(`spawn` の `argsFile`)。Windows のコマンドライン長の
  上限を中継のコマンドラインに持ち込まないためである。

### 2.2 中継が覚えておくもの

リロード中に CLI が出した行を失わないことと、同じ行を二重に処理させないことの両方が要る。
行ごとの通し番号は持たず、**ターン結果(`result` 行)の数**だけを目印にする。

- Unity は `result` 行を処理し終えるたびに `ack {resultsProcessed}` を送る
  (`AgentHub.OnTurnCompleted` の最初の文)。
- 中継は「最後に ack された `result` より後の標準出力」をすべて持つ。
- つなぎ直したとき、中継は次の順に送る: `system/init` 行、`initialize` への応答、
  持っている行すべて、最後に `live`。
- つまり **開いているターンの行は、前のドメインが処理済みの分も含めてもう一度届く**。
  Unity 側はその分の表示を消してから受け取り、いつもの処理経路で作り直す(§5)。

溜めすぎないための規則が 2 つある。

1. トップレベルの `assistant` 行が来たら、それまでの `stream_event`(差分)は捨てる。
   完成した行が差分を置き換えるからである。
2. Unity が `control_response` を書いたら、同じ `request_id` の `control_request` を捨てる。
   答え終えた承認やフックが、つなぎ直しでもう一度出ることはない。

上限は 32 MB。超えたら溜めるのをやめて印を付け、次のつなぎ直しは失敗として扱う
(§7 の「止めて再開」に落ちる)。CLI の出力を読むこと自体は止めないので、CLI が
パイプ詰まりで固まることはない。

## 3. MCP(`uap_*` ツール)

Unity 側の MCP サーバー(`UapOpsHttpServer`)はドメインごとにポートとトークンが変わる。
CLI に渡した接続先が毎回無効になるのでは意味がないので、**CLI には中継の固定の入口**を
教える。中継は受けた POST を、その時点の Unity の入口へ転送する(`backend` フレームで
登録される)。

- Unity が不在の間、中継は要求を持って待つ(既定 25 秒。CLI 側の待ち時間 30 秒より短く)。
- Unity が戻って `backend` を登録したら、持っていた要求を流す。
- リロード直前に Unity 側のキューに残っていた呼び出しは、`503` と `X-Uap-Not-Run: 1` で
  返す(`UapNotRunException`)。中継はこれを「実行されていない」と判断し、次のドメインへ
  届け直す。**始まっていた呼び出しは届け直さない**。結果が分からないので、
  「結果は不明。状態を確かめてから呼び直すこと」というエラーをモデルに返す。
- 待ち時間を過ぎたら「まだリロード中。実行されていないので再試行してよい」と返す。

## 4. 生存管理

| 事態 | 動き |
|---|---|
| エディタを閉じる | `shutdown` を送る。中継は CLI を終わらせてから自分も終わる。終わらなければプロセスを止める |
| エディタが落ちる | 中継が Unity のプロセスを 1 秒ごとに見ており、いなくなれば CLI ごと終わる |
| 切り離したまま誰もつながない | 一定時間(既定 600 秒)で CLI ごと終わる |
| CLI が終わる | つながっていれば `exited` を送る。Unity は今までどおり再起動する |
| 中継が落ちる | 接続が切れる。Unity は CLI が落ちたときと同じに扱う |

孤児の掃除(`ZombieReaper`)の記録には中継のプロセスを書く。CLI は中継の子なので、
中継を止めれば一緒に止まる。

Unity の開始時刻は中継が自分で読んで覚える(`--unity-start-ticks 0`)。Mono と .NET で
開始時刻の値が微妙に違い、Unity から渡した値と比べると誤判定するからである。

## 5. リロードをまたぐ状態の受け渡し

方針: **状態は運ばず、行をもう一度流して作り直す**。`AgentClient` や `AgentHub` の
ターン中の状態を直列化することはしない。

### 5.1 切り離し(`AgentHub.DetachForReload`)

`ReloadLifecycle.OnBeforeAssemblyReload` が `ShutdownForReload` の代わりに呼ぶ。
中継経由でなければ何もせず false を返し、今までの停止が走る。

1. つなぎ直しに要るものを `SessionStateBridge.RelayAttachJson` に書く: 中継のポートと
   トークン、プロセス ID、処理済みの `result` の数、ターン番号と開いているターンの数、
   `initialize` の要求 ID、そして「最後の `result` より後に作ったアシスタント発言の ID」。
   SessionState はエディタのメモリ上にあり、プロジェクトには書かれない。
2. `TearDownClient(detach: true)`。割り込みも停止もせず、`detach` フレームを送って接続を
   閉じる。それ以外の後始末(開いているカードの格下げ、ターンスコープの終了、会話ログの
   保存)は今までと同じである。

### 5.2 つなぎ直し(`AgentHub.TryReattachRelay`)

`ReloadLifecycle.EnsureStartupReconciled` の最初の手順。記録は読んだ時点で消す(一度きり)。

1. 中継につなぎ、`welcome` を確かめる。CLI が動いていない、行を保持しきれていない、
   プロトコルが合わない、のどれかなら失敗(中継には止まるよう伝える)。
2. 記録にあったアシスタント発言を会話ログから消す。これから同じ内容が届き直すからである。
3. MCP サーバーを起動する。ターンが開いていたなら、チェックポイントの記録窓とターン
   スコープを開き直す(送信時と同じ順: 記録窓 → スコープ)。
4. 新しい `AgentClient` を作って `Attach` する。何も書かず、プロセスも起動しない。
   ターン番号と開いているターンの数を戻し、要求 ID の採番を前のクライアントと重ならない
   位置から始める。
5. 最後に `backend` を登録する。中継が持っていた MCP 呼び出しがここで流れる。

届き直した行は `AgentClient.Pump` からいつもの経路で処理され、次のものが作り直される:
ストリーミング中の発言、開いているツールカード、承認待ち(答えていないものだけ)、
フックの問い合わせ、セッション ID と `initialize` の応答。リロード中にターンが
終わっていれば、`result` 行もそのまま届いて普通に完了する。

届き直した行で二重に数えてはいけないものは、再送が終わるまで止める(`IsRelayReplaying`):
チェックポイントのツール集計と、`uap_scripts_commit` によるコンパイル後自動継続の予約。
再送の終わりは、中継の `live` が届き、受信済みの行をすべて処理し終えた時点とする。

「設定を変えたので再接続が必要」の判定に使う起動時の設定の控えも記録に入れて運ぶ。
つなぎ直した CLI は古い設定のまま動いているので、控えを今の設定で作り直すと
再接続の案内が消えてしまうからである。

成功した場合、`ReapOrphansNow`(記録されているプロセスはいまつないだ中継である)、
`RestoreAfterReload`、中断ターンの自動継続は行わない。コンパイル後の自動継続だけは、
リロード前にターンが終わっていた場合に限り今までどおり働く。

### 5.3 割り切った点

- ターンの途中で送ったユーザー発言は、作り直したアシスタント発言より上に並ぶことがある。
- 前のターンから動いているバックグラウンドのサブエージェントは、今までのリロード後と
  同じ見え方になる(タスク ID の対応が失われる)。
- ターンの外で届いた通知行(`result` の後、リロードの前)は二重に出ることがある。
- リロードの瞬間に Unity の中で実行中だったツール呼び出しは「結果不明」のエラーになる。
  二度実行することはしない。
- ターンの途中でパネル自身がアシスタント発言の中に足した注記(スクリプト検証ゲートが
  書き込みを拒否した、など)は、作り直しで消える。ツールカードの失敗表示は残る。
- コンパイルとリロードで 25 秒を超えて Unity が不在だと、その間の MCP 呼び出しは
  「実行されていない、再試行可」のエラーになる。

## 6. 設定

- `PanelSettings.cliRelayEnabled`(既定 false)。変更は次回の接続から効く
  (`SettingsChangeDetector` が再接続を促す)。
- ON にした最初の接続では、中継プログラムのビルドが終わっていなければ今までの方式で
  つなぐ(ビルドは裏で進み、次の接続から中継になる)。理由はログに 1 回だけ出す。

## 7. 「止めて再開」に落ちる条件

設定が OFF、Claude Code 以外のバックエンド、中継がビルドできない・起動しない、
切り離しの時点でクライアントが動いていない、つなぎ直しで中継に届かない、CLI が
リロード中に終わっていた、行を保持しきれなかった、プロトコルが合わない。
どれも今までのコード経路をそのまま通る。

## 9. 検証

- スモークテスト(`ci/SmokeTests`、`CliRelayCoreSmoke`): バッファの規則、ack による
  切り詰め、上限超過、HTTP の解析、転送結果の分類。
- 結合テスト(`ci/RelayLive`): 中継を実プロセスで起動し、偽 CLI を相手に、切り離し中の
  出力の保持、つなぎ直しでの再送、MCP の保留と転送、Unity 不在時の自動終了を確かめる。
- EditMode: `AgentClientAttachTests`(Attach / Detach)、`UapMainThreadDispatcherTests`
  (実行前の呼び出しだけが「未実行」になる)。
- 実リロード(`CliRelayReloadLiveTests`、カテゴリ LiveReload、`UAP_FAKE_CLI` が要る):
  1. ストリーミング中にスクリプトリロード → 同じ中継・同じ CLI のまま、割り込みも
     `--resume` もなく、60 行すべてが会話ログにちょうど 1 回ずつ出る。続けて次の
     メッセージも同じ CLI が受ける。
  2. 承認待ちの最中にリロード → リロード後も承認待ちが 1 件だけ出ており、答えると
     CLI に 1 回だけ届く。
  3. 切り離した直後に中継を止める → つなぎ直しは失敗し、今までどおり `--resume` で
     再開する。
- Unity 2022.3.62f3(Linux)で上の 3 件を含む EditMode 全件を実行して確認した。
- 実装後に 5 観点(トランスポート、通信の取り決め、ハブの状態、プロセスの生存、設定 OFF 時の
  退行)でレビューし、反証を経て残った 13 件のうち 12 件を直した。主なもの: 送信が途中で
  失敗したリンクは捨てる、中継が自分で閉じたあとは記録済みの PID を止めない、起動に
  失敗した中継を残さない、「未実行」の 503 を書き終えてからリスナーを閉じる、中継の
  停止処理が詰まった標準入力の書き込みを待ち続けない。残した 1 件は §5.3 の注記の件。

## 10. 今後

- CLI の MCP 呼び出しの待ち時間を伸ばせるか実測し、保留時間を 25 秒より長くする。
- 切り離しが長引いたときにフックの問い合わせへ中継が代わりに答える。
- 再送中だけ 1 フレームあたりの処理行数を増やし、長いターンの作り直しを速くする。
- Windows と macOS での実機確認(コンソール窓が出ないこと、エディタを強制終了したときに
  中継と CLI が残らないこと)。確認が済むまで既定は OFF のままにする。
- ACP バックエンドへの対応。
