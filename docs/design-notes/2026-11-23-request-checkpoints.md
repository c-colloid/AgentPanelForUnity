# 2026-11-23 -- 依頼ごとのチェックポイント(「この依頼を元に戻す」)

発端: 「Undo できない場合の方が多く感じる。ドメインリロードを挟んでも Undo できる仕組みを
作れないか」というユーザー報告。切り分けの結果、ユーザーの見え方は「Edit メニューに
Agent turn は出ていて、押すとシーンだけ戻る」に近い(確証なし)。

参照: `Editor/Ops/UapTurnScope.cs`、`docs/design-notes/2026-08-01-phase5-unity-ops-design.md`
§1.3 / §8.2 B2、`docs/design-notes/2026-09-06-domain-reload-resilience-and-hot-reload.md`。

---

## 0. 結論(先に)

- Undo が効かない主因はドメインリロードではなく、**ファイル変更が Unity の Undo の対象外**で
  あること。エージェントの依頼の大半はスクリプトやアセットのファイル変更を含むので、
  Ctrl+Z は「シーンだけ戻り、ファイルは残る」半端な結果になる。
- 対策として、Unity の Undo とは別に **依頼単位のチェックポイント**をディスクに持つ。
  依頼がファイルを変える直前にその内容を `Library/AgentPanel/Checkpoints` へ退避し、
  会話ログの「この依頼を元に戻す」でファイルの書き戻しとシーンの Undo をまとめて行う。
  ディスク上にあるので、ドメインリロードもエディタ再起動も越える(シーンの Undo 部分は
  エディタ再起動を越えない。§4)。
- 最初の版の決め打ち: **巻き戻しは最も新しい依頼からのみ**、**やり直し(Redo)なし**。

## 1. 現状の棚卸し

| 範囲 | Undo 可 | Undo 不可 |
|---|---|---|
| `uap_*` ツール(このパッケージ) | 13(シーン・コンポーネント・プロパティ・Transform 系) | アセット作成/削除、`uap_scripts_commit`、メニュー実行、`uap_execute_code`、シーンを開く/保存 ほか |
| CLI 自身の Edit / Write / Bash | なし | すべて(ファイル変更) |

ターン = 1 Undo グループ(`UapTurnScope`)は、Undo に載る操作にしか効かない。加えて、
ターン途中でリロードが入ると自動継続は別ターン(別グループ)になり、1 回の依頼が
Ctrl+Z 1 回では戻らない。

`UapTurnScope` のコメントは「Undo 履歴はドメインリロードを綺麗に越えない」としていたが、
実測した記録は無かった。本変更の実機テスト(§8)がこれを確かめる。

## 2. 変更前のファイルをどう捕まえるか

チェックポイントは「変更の**直前**の内容」が要る。変更後に気づいても遅いので、経路ごとに
事前に呼ばれる場所を使う。

| 経路 | 捕まえ方 | 確かさ |
|---|---|---|
| Claude Code 自身の Write / Edit / MultiEdit / NotebookEdit | 制御プロトコルの PreToolUse フック(下記) | 実測済み。全権限モードで書き込み前に届く |
| Unity のアセットデータベース経由の保存・作成・移動・削除 | `AssetModificationProcessor`(`UapCheckpointAssetWatcher`) | どのツール・メニュー・エディタコードが原因でも拾う |
| ツールが自分でファイルを書く箇所 | そのツールが `UapCheckpointRecorder.Capture` を呼ぶ(`uap_scripts_commit`、Web 取り込み) | 呼び出しを入れた箇所のみ |
| シェル(Bash / PowerShell)、任意のエディタコード | 捕まえない。ツール名と回数だけ記録し、巻き戻し時に「追跡していない」と表示 | -- |
| Claude Code 以外のエージェント(ACP)自身のファイル編集 | 捕まえない(フックは Claude Code の制御プロトコル) | 新規ファイルは下記の .meta 経路で拾える |

### 2.1 PreToolUse フック(実測)

`initialize` の control_request に
`hooks: { PreToolUse: [{ matcher: "Write|Edit|MultiEdit|NotebookEdit", hookCallbackIds: ["uap_checkpoint"] }] }`
を載せると、該当ツールの実行前に CLI が `hook_callback` の control_request を送り、
control_response が返るまでツールを実行しない。CLI 2.1.330 で確認した内容:

- `--permission-mode acceptEdits` でも届く(このモードでは `can_use_tool` は来ないので、
  既存の権限経路では書き込み前を捕まえられない)。
- コールバックを受けてから 1 秒応答を遅らせても、その間ファイルは変更されない
  (Write は未作成のまま、Edit は旧内容のまま)。
- `input.tool_name` と `input.tool_input.file_path` が載る。
- 応答は `response: {}`(判断なし)で、ツールは通常の権限経路へ進む。

`AgentClient` は `hook_callback` を受けたら `HookCallbackReceived` を発火し、購読側が何を
しても(例外を投げても、購読が無くても)必ず応答を返す。応答しないフックは「固まった
ツール」と見分けがつかないため。フックは `initialize` で 1 回だけ登録するので、設定の
切り替えは再接続で反映する(`SettingsChangeDetector.RequiresReconnect`)。

既存のスクリプト検証ゲートのフック(`--settings` の PowerShell フック、Windows のみ)とは
別経路で、両方が同時に動く。

### 2.2 アセットデータベース経由

`OnWillSaveAssets` / `OnWillDeleteAsset` / `OnWillMoveAsset` / `OnWillCreateAsset` は操作の前に
呼ばれる。記録中だけ働き、操作自体には一切介入しない(常に「未処理」を返す)。

新規アセットは、Unity が書く `.meta` の作成通知で分かる。`.meta` が今まで無かったファイルは
新規とみなす(ファイル本体は通知時点で既にディスクにあるため、「存在しなかった」ことを
直接は観測できない)。この推定が外れるのは「`.meta` の無い既存ファイルが依頼中に初めて
インポートされた」場合で、その場合も巻き戻しが消したファイルは §4 の退避先に残る。

ターン末の `AssetDatabase.Refresh()` が取り込むアセットも依頼のものとして記録するため、
記録の終了は Refresh の後に置いた(`UapTurnScope.EndIfActive`)。

## 3. 記録庫(`UapCheckpointStore`)

Unity 非依存の純粋なファイル IO + JSON。`ci/SmokeTests` が実コードをそのまま動かす。

```
Library/AgentPanel/Checkpoints/
  <id>/manifest.json   依頼 1 件の記録
  <id>/files/<n>.bin   変更前の内容(エントリごと)
  <id>/redo/<n>.bin    巻き戻しが上書き・削除したもの(index.txt に元パス)
```

- **最初に触れた時点が勝つ**: 同じファイルを依頼中に何度書いても、エントリは依頼前の内容 1 つ。
- 存在しなかったパスは「依頼が作成した」と記録し、存在しなかった親フォルダも同様に記録する。
- 上限: 1 ファイル 128 MB、1 依頼 512 MB、全体で 20 件・2 GB。超えたファイルは内容を
  保存せず「戻せない」と記録する(巻き戻し時に件数を出す)。古い依頼から削除する。
- 何も記録しなかった依頼(質問だけ等)は、次の依頼の開始時に消す(20 件の枠を使わせない)。
- 記録対象はプロジェクトフォルダ内のみ。`Library/` `Temp/` `Logs/` `obj/` `.git/` は除外。
  マニフェストは読み込み時にもパスを検証する(巻き戻しはマニフェストが指すパスに書くため)。
- ターン終了時に各ファイルのサイズと更新時刻を控え、巻き戻しの確認ダイアログで
  「依頼の後に変更されたファイル数」を出す。

### 依頼の単位

- ユーザーが書いたメッセージがターンを開始するとき、新しいチェックポイントを開く。
- パネルが自動で送る継続(コンパイル後・中断後)は、同じチェックポイントを開き直す。
  リロードで分かれた依頼も 1 件として戻せる。
- 実行中のターンへの追加送信は、開いているチェックポイントにそのまま入る。
- 記録の窓はリロードをまたがない(リロード後にエディタが取り込むものは依頼の作業ではない)。
  記録庫はディスクにあり、「会話の最後のチェックポイント」は SessionState に持つ。

## 4. 巻き戻し

対象は **最も新しい、未巻き戻しで、何かを記録した依頼** 1 件だけ(プロジェクト全体で 1 つ。
ファイルの状態は会話をまたいで共有されるため)。途中の依頼だけを戻すと後の依頼の変更と
衝突するので、新しい順にしか戻せない。戻すと 1 つ前が対象になる。

手順:

1. **シーン**: 依頼が Undo 対象の操作をしていれば `Undo.RevertAllDownToGroup` で依頼の最初の
   グループまで戻す。Unity の Undo は 1 本のスタックなので、依頼より後の手動編集も一緒に
   戻る(確認ダイアログに明記)。Undo 履歴はエディタのプロセスと運命を共にするため、
   記録時と起動が違えば「シーンの編集は取り消せない」と表示する(起動の識別は
   SessionState に置いた ID。SessionState もリロードは越え、再起動で消える)。
2. **ファイル**: 新しいエントリから順に、依頼前の内容を書き戻し、作成されたファイルと
   その `.meta` を削除し、作成されたフォルダは空なら削除する。上書き・削除する前の内容は
   `redo/` に退避する(パネルに Redo は無いが、手作業で取り戻せる)。
3. **開いているシーンのファイル**: 依頼開始時に未保存の変更が無かったシーンは、ファイルを
   戻してディスクから読み直す。未保存の変更があったシーンはファイルを戻さない(戻すと
   その変更が消える)。メモリ上は 1. の Undo で戻り、保存するかはユーザーが決める。
4. 会話ログへの記録とモデルへの通知(§6)を先に済ませてから `AssetDatabase.Refresh()`。
   スクリプトを戻すとコンパイルとドメインリロードが始まるため。

実行できない場合: ターン実行中、Play モード中、コンパイル中、対象が既に無い。理由を
会話ログに出す。

## 5. UI

- ユーザーメッセージの役割行の右端に「この依頼を元に戻す」(テキストリンク)。出るのは
  巻き戻せる 1 件のメッセージだけで、ターン実行中は出ない。表示の有無は行のシグネチャに
  含め、状態が変わると行を作り直す。
- 押すと確認: 戻すファイル数と削除するファイル数、当てはまる注意(依頼後に
  変更されたファイル、保存されなかったファイル、シーンの Undo、追跡していないツール)。
  最初の版は Unity 標準のモーダルダイアログだったが、§11 でパネル内の確認カードに替えた。
- 設定「依頼ごとにチェックポイントを残す」(既定 ON)。

`uap_*` ツール別の「Undo 可否」表示とターン末の警告(§8.2 B2)は従来どおり。

## 6. モデルへの通知

巻き戻しはモデルの知らないところで起きる。放置するとモデルは自分が作ったファイルや
オブジェクトがまだあるものとして続けてしまうので、同じ会話の次のユーザーメッセージの
先頭に英語の通知を付ける(戻したファイル数、シーンの扱い、追跡していないツール、
「ファイルを読み直してから使うこと」)。スラッシュコマンドには付けない(先頭に文があると
コマンドとして読まれないため、次の通常メッセージまで待つ)。SessionState に置くので
巻き戻し直後のリロードも越える。

## 7. 制限(最初の版)

- シェルコマンド、`uap_execute_code`、メニュー実行による変更は、アセットデータベースを
  通らない限り追跡しない。
- Claude Code 以外のエージェント(ACP)自身のファイル編集は、既存ファイルの上書きを
  捕まえられない。
- アセットデータベースを通さずにファイルを直接書くツールは、`Capture` を呼ぶ箇所を
  入れたものだけが対象。
- リロード中断の直後(継続ターンが始まる前)にエディタが取り込んだ新規ファイルの `.meta` は
  記録の窓の外。ファイル本体が記録されていれば、巻き戻しは対の `.meta` も削除する。
- 依頼の実行中にユーザーが手で保存・追加したアセットも、その依頼の変更として記録される。
- 複数シーンを開いている場合、巻き戻したシーンファイルの読み直しは Unity の
  「外部で変更された」ダイアログに任せる。
- 途中の依頼だけを戻すこと、Redo はできない。

## 8. 検証

- **フックの実測**(§2.1): 実 CLI 2.1.330 を stream-json で起動し、acceptEdits モードで
  Write と Edit を実行させて確認した。
- **スモーク(Unity なし、`ci/SmokeTests`)**: 記録庫の捕捉・巻き戻し・上限・削除・マニフェスト
  検証、および判断ロジック(`UapCheckpointPolicy`)。ローカルで 753 件成功。
- **EditMode**: `UapCheckpointRecorderTests`(記録の窓、継続での開き直し、新しい順の規則、
  シーンの Undo、実アセットデータベースでの作成・削除の検知)、`AgentClientHookCallbackTests`
  (登録と、必ず応答すること)。
- **実リロード**: `UapCheckpointReloadLiveTests` が、依頼を記録 → 実ドメインリロード →
  巻き戻しを通し、ファイルの復元と、リロード前に記録した Undo グループでシーンの
  オブジェクトが消えることを確認する。後者が §1 の未確認事項の答えになる。失敗する場合は
  シーン編集にも Undo とは別の記録が必要、という結論になる。

### 8.1 実機結果(同日追記)

CI の EditMode ジョブ(Unity 2022.3.22f1、GameCI の Linux コンテナ、バッチモード、
コミット `fbd21f4`)で全件成功した: 通常ホスト 5577 件中 5537 成功 / 0 失敗 / 40 スキップ、
Core 単体ホスト 4342 件中 4315 成功 / 0 失敗 / 27 スキップ。上の 3 フィクスチャは両方の
ホストで全件成功。

`UapCheckpointReloadLiveTests` も成功したので、§1 の未確認事項は次のとおり確定した:
**Unity の Undo 履歴はドメインリロードを越える。** リロード前に記録した Undo グループの
番号で、リロード後に `Undo.RevertAllDownToGroup` を呼ぶと、リロード前に作ったオブジェクトが
消える。`UapTurnScope` の旧コメント(「綺麗に越えない」)は誤りだった。従って、シーン編集に
Undo とは別の記録を持つ必要は今のところ無い(エディタ再起動を越えたい場合を除く)。

確認できていない範囲: Windows / macOS の実エディタ、Unity 6 系(このジョブのマトリクスは
2022.3 のみを選んだ)、ウィンドウを開いた状態でのボタンと確認ダイアログの見た目。

## 10. 追跡していなかった経路への対応(同日追記)

ユーザーからの追加依頼: 「Bash、メニュー実行、`uap_execute_code` も、実行するコードに Undo の
記録を入れれば巻き戻せないか」。エディタ内で動くコードには一部効くが、Bash は Unity の外の
プロセスなので Undo が届かない。どれも「コードに手を入れる」より「実行の前後をパネルが挟む」
方が確実なので、次の順で入れた。§2 の表と §7 の制限のうち、この節と食い違う箇所は
この節が新しい。

### 10.1 ターンが残した Undo 記録を、履歴そのものから検出する

これまで巻き戻しが Undo を使うのは「Undo 対象の `uap_*` ツールを呼んだ依頼」だけだった
(ツール名からの推定)。自前で Undo を呼ぶ `uap_execute_code` のスニペットや、自前で Undo を
登録するメニューは数に入らず、Undo 履歴に記録があるのに巻き戻しで戻らなかった。

ターン開始時と、ターン末のグループ統合の直前に Undo スタックの件数を読み
(`UapUndoProbe`。`uap_execute_code` が使っていた内部 `Undo.GetRecords` への
リフレクションを共有化)、増えていれば `UapCheckpoint.UndoRecorded` を立てる。巻き戻しは
`SceneOps > 0 || UndoRecorded` で Undo を使う。リフレクションが使えない版では従来どおり
ツール数だけで判断する。

### 10.2 実行前後のファイル一覧の比較

`UapCheckpointStore.Scan` が Assets / Packages / ProjectSettings 以下の全ファイルの
サイズと更新時刻、およびフォルダを列挙する(内容は読まない。名前が `.` で始まるフォルダと
リンク先には入らない)。

- 「前」は、そのターンで最初に追跡外の作業が始まる直前に 1 回だけ取る: シェルコマンドの
  実行前フック、`uap_execute_code` の実行直前、メニュー実行の直前。追跡外の作業が無い
  ターンは走査しない(大半の依頼は走査コストを払わない)。
- 「後」はターン末(Refresh の後)に取り、差分を記録する。
  - 増えたファイル・フォルダ → 「依頼が作成した」(巻き戻しで削除)。
  - 変わった・消えたファイルで、まだエントリが無いもの → 内容なしのエントリ
    (`untracked`)。巻き戻しでは戻せないが、確認ダイアログに件数、会話ログに名前が出る。
- 走査が 40 万ファイルを超えたら打ち切り、そのターンは差分を取らない(不完全な一覧で
  差分を取ると、読めなかったファイルを「消えた」と誤認するため)。

既知のノイズ: ターン中に Unity 自身やユーザーが書き換えたファイル(ProjectSettings の保存、
ユーザーが追加したアセット等)も、追跡外の作業があったターンでは差分に入る。

### 10.3 シェルコマンドの書き込み先の事前退避

フックの matcher に `Bash|PowerShell` を足した。実行前にコマンド文字列が届くので、
`UapCheckpointPolicy.ShellTargets` が書き込み先を読み取る: スクリプト検証ゲートの走査
(リダイレクト、`tee`、`sed -i`、`cp` / `mv` / `install` / `dd`、PowerShell の書き込み・コピー系、
.NET のファイル書き込み)に、削除と移動の引数(`rm` / `del` / `Remove-Item`、`mv` の移動元 等)を
足したもの。フォルダは中のファイル、最後のパス要素のワイルドカードは展開する。

読み取りは当て推量なので、**今ある**ファイルだけを退避し、「作成された」とは記録しない
(`cd` の後のコマンドなどでパスの解釈を誤っても、後で無関係なファイルを消すことがない)。
作成の判定は 10.2 の差分だけが行う。変数で組み立てたパス、コマンドが呼ぶスクリプト内の
書き込みは読み取れず、10.2 で「戻せないファイル」として名前が出る。

### 10.4 実行前にシーン全体を Undo に登録する

`uap_execute_code` とメニュー実行の直前(記録中のターンで最初の 1 回だけ)に、読み込み済み
シーンの全ルートオブジェクトへ `Undo.RegisterFullObjectHierarchyUndo` を呼ぶ。コードが Undo を
一切呼ばなくても、ターンの Ctrl+Z と「この依頼を元に戻す」でシーンが実行前の状態に戻る。

入れる前に CI で計測した(Unity 2022.3.22f1、Linux バッチモード。計測用のテストは結果を
ここに写して削除した)。

| Undo を呼ばずに行った変更 | スナップショットへの巻き戻しで戻るか |
|---|---|
| Transform の値の変更 | 戻る |
| オブジェクト名の変更 | 戻る |
| コンポーネントの追加 | 戻る(消える) |
| コンポーネントの破棄(`DestroyImmediate`) | 戻る(復活する) |
| 子オブジェクトの追加 | 戻る(消える) |
| 子オブジェクトの破棄(`DestroyImmediate`) | 戻る(復活する) |
| **新しいルートオブジェクトの作成** | **戻らない**(誰の階層にも属さないため) |

| オブジェクト数(各 2 コンポーネント) | 登録 | 巻き戻し |
|---|---|---|
| 2,000 | 19 ms | 67 ms |
| 20,000 | 212 ms | 2,428 ms |

判断と実装:

- 登録は 1 オブジェクトあたり約 10 マイクロ秒で、スニペットやメニューの実行前の待ちとして
  許容できる。上限を 5 万オブジェクト(約 0.5 秒)に置き、超えるシーンでは取らずにログへ
  出す。巻き戻しの 2.4 秒は、ユーザーがボタンを押したときだけ払う。
- 戻らなかった「新しいルート」は、スナップショット時点のルートの集合を覚えておき、
  ターン末(Undo グループ統合の直前)にそこに無いルートへ `Undo.RegisterCreatedObjectUndo` を
  後付けすることで埋める。ツールが既に登録済みのルートには二重の記録になるが、
  巻き戻しで問題が出ないことをテストで固定した。
- Play モード中は取らない(その変更は Play 終了で破棄される)。
- スナップショット自体が Undo 記録なので、取ったターンは 10.1 の `UndoRecorded` が立つ。
- `uap_execute_code` の応答に `sceneSnapshotNote` を足し、「シーンオブジェクトへの変更は
  Undo を呼ばなくても戻せる。アセットへの変更は対象外」とモデルに伝える。

対象外のまま残るもの: スニペットやメニューがアセットのオブジェクト(マテリアルの値など)を
Undo なし・保存なしで書き換えた場合。保存されればアセットデータベースの経路で拾える。

### 10.5 実機結果

CI(コミット `d26dca3`、Unity 2022.3.22f1)で 10.1〜10.3 のテストを含む全件が成功した:
通常ホスト 5586 件中 5546 成功 / 0 失敗、Core 単体ホスト 4351 件中 4324 成功 / 0 失敗。

10.4 の実装後(コミット `9b9ed33`、同じ環境)も全件成功した: 通常ホスト 5586 件中 5546 成功 /
0 失敗、Core 単体ホスト 4351 件中 4324 成功 / 0 失敗。Undo を呼ばないコードによる変更
(値・名前・コンポーネントの追加・子の追加と破棄・新規ルート)がすべて巻き戻ること、
ツールが登録済みのルートへの二重の作成記録がエラーを出さないことを確認した。

### 11.3 数え方(`UapCheckpointPolicy.IsDisplayFile`)

「利用者がその依頼のファイルと呼ぶもの」だけを数え、一覧に出す。

- フォルダは数えない(空になれば巻き戻しの結果として消えるだけ)。
- `X.meta` は、`X` 自身がチェックポイントにあるときは `X` に含める。`.meta` だけが変わった
  場合(インポート設定の変更)は 1 個と数える。
- 確認カードの数、結果表示の数、モデルへの通知の数はすべてこの規則を通す。記録庫が
  実際に戻す対象は変わらない(`.meta` もフォルダも従来どおり処理する)。
- 「依頼の後に編集されたファイル」は、巻き戻しが実際に書き換える・削除するファイルだけを数える。

### 11.4 カードの構造

1. タイトル(太字)「この依頼を元に戻しますか?」
2. 起きること(通常色、1 行 1 件): ファイル(復元と削除のどちらがあるかで文面を選ぶ)、シーン。
   何もできない依頼は「自動では元に戻せません」の 1 行で、[元に戻す] は無効。
3. 実行前に知ること(当てはまるものだけ。左に警告色の線): 後から手作業で行ったシーン編集も
   取り消される / 依頼後の編集が失われる / コマンドで変更され復元できない / 大きすぎて
   退避できなかった / ほかの変更が残りうる実行。
4. 対象のファイル(既定で折りたたみ。開閉状態は行の作り直しをまたいで保持)。
5. フッター(上に区切り線): 「この操作はやり直せません。」と [元に戻す](主)[キャンセル]。

Esc はターン中断に割り当て済みなので、カードはキー操作を持たない。赤い塗りのボタンは
使わない(停止ボタン専用)。

### 11.5 見送ったもの

- 戻せるものが 1 つも無い依頼が最新のとき、それより前の依頼を戻せなくなる件。「新しい順に
  のみ」の決め事に関わるので、表示(11.4 の 2)だけにとどめた。

- コンパイル開始や Play 突入の瞬間にリンクを消すこと(次の再描画までは残る。押しても
  `RevertRequest` が理由を出して断る)。
- カードを開くたびに `Describe` がマニフェストを読み直すこと(開いている間の行の作り直しは
